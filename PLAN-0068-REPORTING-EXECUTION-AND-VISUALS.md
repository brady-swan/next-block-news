## 1. Repair the handoffs that strand completed work

### Event identity and retry memory

Evidence: CLARITY reached the original Semafor report, but the writer supplied a broad storyline
as an exact event key. It was held before the editor. Bit2Me repeatedly mixed a new-event relation
with an already assigned canonical event. Later identity failures were absent from useful retry
memory, leaving an obsolete research objective or an empty editor-feedback state.

Changes:

- Clearly separate **exact event**, **broader storyline**, **open draft** and **confirmed earlier
  output** in existing packet labels and dossier field descriptions. Include one compact example:
  a new development may belong to the CLARITY storyline without sharing the Lummis event key.
  Use `material_update` for the applicable existing-event/output relationship, not merely because
  the topic has appeared before. Keep same-event draft enrichment separate from a new event.
- Give invalid submissions a precise, code-derived correction: the failing field, supplied
  allowed event keys, known current member identity and actual output state. Do not ask for more
  corroboration when the failure is identity. Reuse the existing bounded finalization/repair path;
  allow at most one identity correction, within the same six-response/360-second writer limits,
  sharing—not stacking with—the current receipt-repair allowance. No extra research loop.
- Validation before correction must be side-effect-free: no alias reservation, storyline update,
  notebook acceptance or publisher mutation from an invalid attempt. Commit the final accepted
  outcome once; preserve usable sibling stories rather than rerunning the whole desk.
- Carry later pre-editor deferrals into the existing compact retry context with their actual
  reason/time and actionable objective. If canonical identity is not yet safe, associate the
  diagnostic with validated candidate IDs/run observations, not a guessed event notebook.
  Reuse existing storage/read-time projections rather than add another memory subsystem.
- Preserve the distinction between a writer proposal, editor decision, staged draft and confirmed
  publication. An empty editor response must not be presented as a completed editor review.

Never silently turn a storyline into an event, infer an alias from a title, or automatically
publish/reopen an old item. If correction cannot fit or resolve the ambiguity, retain the work
and exact failure for the next normal eligible run.

Acceptance: CLARITY and Bit2Me fixtures receive the right repair instruction without losing
receipts; exhausted/no-identity cases remain honest and recoverable; no duplicate or arbitrary
canonical mutation; the next packet shows the latest failure rather than the old one.

### Editor response contract

- Keep the current human-draft fallback if review remains unavailable, with a conspicuous
  “Needs human review — editor response failed” status in the existing Desk story/output view.
  Do not rename fallback to approved or silently change publication policy.

Acceptance: Treasury/gold/AUSTRAC/Metaplanet failure fixtures, text-only and real-image responses,
partial valid batches, deadline exhaustion and provider refusal all retain correct outcomes.
Real images still reach the editor as pixels; a simpler text schema cannot bypass image review.

## 2. Close the gap between research and the reader

Evidence: Treasury's original PDF and Canada's official material were obtained, but readers
still received social-tip links. Zondacrypto reached the original announcement but missed the
later detention outcome. This calls for better use of work already available, not blanket
additional verification.

Changes:

- Let the editor optionally select a **reader receipt reference** from the exact inspected
  evidence supplied for that story, including explicitly selected relevant appendix evidence.
  Default to the writer's selected receipt. The model returns a code-issued reference, never
  a newly invented URL. It may retain good original journalism over a less useful official page.
- Resolve that choice through the existing receipt catalog. Carry the same final source through
  the first Typefully reply, provenance/classification, notebook, Desk, immutable delivery payload
  and replacement comparison. Supporting receipts remain separate; changing the reader link
  neither fabricates corroboration nor requires one page to support every harmless detail.
- Preserve direct capture versus native paraphrase, source attribution, clipping limits and
  dates. A malformed receipt selection enters bounded recovery; fallback keeps the previously
  valid receipt. Never create a mismatch between displayed source and actual delivery.
- Give selected evolving stories a targeted current-state check using existing evidence,
  `search_intake` and memory: did later reporting change “requested” to “approved,” “promised”
  to “returned,” or another material outcome? This is selective judgment, not a mandatory
  second search for every post.
- Refine preparation guidance so relevant follow-up evidence in its eligible inventory is not
  rejected solely because it is insufficient for a second standalone post. Use the existing
  related-key/event-group organization. Background still stays out of the default writer packet;
  the writer can deliberately search skipped intake when useful. No new discovery/triage stage
  or all-day dump of background material.
- Make freshness guidance concrete: distinguish original disclosure, later outcome, reporting
  period and article timestamp. Use absolute dates where a staged draft may wait for its owner.
  No new hard age cutoff; a fresh earnings disclosure can legitimately describe an older quarter.

Acceptance: Treasury/Canada can select their inspected original receipt; Zondacrypto's later
outcome can enrich the selected story without manufacturing a duplicate; an unknown/unseen
reference cannot be used; main copy/source reply and saved provenance agree after replacements.
No mutation of any owner-commented draft during tests or rollout.

## 3. Sharpen selection and finish the copy

Use a few observed examples in the existing writer/editor guidance, not another editorial
handbook or another model. Replace/refine overlapping instructions rather than keep appending.
These proposed lines are included explicitly for Brady's review:

> Choose the development that matters to a Bitcoiner, not necessarily the source's headline.
> A mining company's earnings may contain a meaningful mining-business story even when its
> promotional headline is another treasury record. Routine treasury purchases remain high-bar.
>
> General crypto-industry enforcement is not automatically a Bitcoin story. Identify the
> concrete Bitcoin consequence or unusually consequential monetary development; do not add a
> token Bitcoin sentence to make an otherwise off-beat item fit.
>
> Lead with the finding or change. Keep only the context that changes the reader's picture.
> Use single sentences or two-sentence short paragraphs with blank lines between each.
> Avoid back-to-back complex sentences. A follow-up should not repeat the old draft's inventory.

Examples: Glassnode is useful research without a trading take; Metaplanet needs a focused
development, not all the option-pool mechanics; AUSTRAC's routine crypto/remittance tally is
an owner-rejected selection; Canaan's revenue/hardware decline is a possible stronger angle,
not a requirement to cover every miner's earnings. Preserve the existing Bitcoin/monetary remit,
treasury-company bar and room for model judgment. Add no scoring model or deterministic style gate.

Acceptance: owner examples remain recognizable in focused prompt regressions and review samples;
good concise copy survives, off-beat copy is not merely shortened, and later-event qualifications
are not removed in the name of brevity.

## 4. Use the visual capability we already shipped

Evidence: three owner comments identified useful charts. The Mempool writer asked for image
inspection despite already having that tool. No natural image path has yet been demonstrated.

Changes:

- Add a compact pointer on relevant existing lead/receipt cards that an image is available,
  with origin/date and the tool to open it. Prefer actual post/article media over avatars,
  duplicate thumbnails and navigation images when selecting the existing bounded image list.
  Keep the same list and encoded-image caps; do not automatically inject every image's pixels.
- Explain that inspection can help **understand a lead**, not just decorate an already written
  post. Unknown reuse rights do not prevent inspection; they still prevent automatic attachment
  under the current policy. Do not silently broaden that policy in this sprint.
- Put two compact, valid `render_visual` examples next to its guidance: a sourced bar comparison
  and a dated time series. Reuse existing templates, evidence IDs, rendering and delivery.
- Encourage a real original NBN graphic when inspected data supports it. If reproducing a source
  chart is not permitted, an independently designed chart from adequately sourced facts can
  be useful; do not trace a protected graphic or invent values from an unlabeled axis. Text only
  remains fine when data, relevance, rights, time or legibility do not support a worthwhile image.
- Writer checks actual pixels, units/periods and alt text; editor reviews the same final pixels
  and copy. Use the verified source handle where useful and keep the source/credit in the first
  reply. Preserve existing owner edits/comments and image-dependent-copy handling.

Proposed short guidance:

> When the story turns on a comparison or trend, consider showing it. Inspect a relevant source
> chart, or make an original NBN chart from the evidence using the existing renderer. A useful
> image helps readers understand the story at a glance, making it easier to engage with and
> share, which can extend its reach. Aim for one
> clear takeaway, not extra decoration. Image tools can also help you understand an image-only
> lead. If an image would not improve this post, finish the text and move on.

### Three review cases

1. **Glassnode:** inspect the source's bar chart, preserve what its statistical comparison
   actually measures, and credit/tag Glassnode. Use the source image only when permitted;
   otherwise render our own comparison if its exact data is available. Do not turn correlation
   or explanatory power into an unsupported causal claim.
2. **Metaplanet:** inspect the “underperforms” comparison; retain its benchmark, dates and units.
   A concise supported comparison may communicate more than repeating governance mechanics.
3. **Treasury:** Brady means the recent increased operations—his $4B → $8B → $12.5B sequence—
   not the 2024 launch. Research the actual announcements/results and date the change. Check
   whether these are like-for-like operation maxima, weekly totals or completed purchases,
   including cash-management versus liquidity-support differences. Plot comparable quantities,
   label scheduled maxima as such, and separate actual results if both are shown. The sequence
   is the research brief, not yet a verified dataset. Do not force a misleading escalation chart.

Acceptance: render and inspect representative source-backed original charts locally; exercise
the actual model/tool flow in an isolated bounded replay with no publishing side effects. After
deployment, observe an organically appropriate writer-created visual reaching editor/Desk and,
if normally approved, Typefully. A synthetic upload test is not proof of editorial adoption.
No compulsory image count, extra image model, worker or automatic late-image rewrite.
